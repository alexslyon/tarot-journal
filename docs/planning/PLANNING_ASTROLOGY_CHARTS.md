# Astrological Chart Integration — Planning Document
*Decisions made in design review session, March 2026*

This document covers the design and data model for automatic astrological chart generation within the Tarot Journal app, using the Kerykeion Python library.

---

## Overview

Automatic generation of astrological charts from date, time, and location data already stored in the app. Two chart types in the initial implementation:

- **Natal charts** — generated from profile birth data, displayed on the Profiles view
- **Event charts** — generated from journal entry reading datetime and location, displayed on the Entry viewer

Charts are generated using Kerykeion (Python, Swiss Ephemeris) running locally in the Flask backend. No external API or internet connection required.

---

## Dependencies

- **Kerykeion** Python library (`pip install kerykeion`)
- Kerykeion includes Swiss Ephemeris data files; no separate ephemeris installation needed
- **Licensing note:** Swiss Ephemeris is dual-licensed (AGPL or commercial). AGPL is fine for personal use but relevant if the app is ever distributed commercially.

## Chart Types

### Natal Chart (Profiles)
Generated from a profile's birth_date, birth_time, birth_place_lat, birth_place_lon.

**Required fields:** All four must be populated to generate a chart. If any are missing, no chart is generated — show a message indicating which fields are needed.

**birth_time is particularly important** — without it, house positions and the Ascendant are meaningless. If birth_time is missing but the other three fields are present, consider offering a "solar chart" (noon default) with a clear disclaimer, or simply don't generate. Decide during implementation.

### Event Chart (Journal Entries)
Generated from a journal entry's reading_datetime, location_lat, location_lon.

**Required fields:** All three must be populated. If location is missing but datetime exists, no chart is generated — prompt the user to add a location.

## Data Model

### Table: `chart_cache`
Stores both the rendered SVG and the structured chart data for each generated chart.

| Column | Type | Notes |
|--------|------|-------|
| id | integer | PK |
| source_type | text | "profile" or "entry" |
| source_id | integer | FK → profiles.id or journal_entries.id depending on source_type |
| house_system | text | House system used for this chart (e.g. "Placidus", "Whole Sign") |
| chart_svg | text | Complete SVG string as generated by Kerykeion |
| chart_data | text (JSON) | Structured chart data — planetary positions, house cusps, aspects. See schema below. |
| input_hash | text | Hash of the input parameters (date, time, lat, lon, house system). Used to detect when regeneration is needed. |
| created_at | datetime | |
| updated_at | datetime | |

**UNIQUE constraint** on (source_type, source_id) — one cached chart per profile or entry.

### chart_data JSON schema

```json
{
  "planets": [
    {
      "name": "Sun",
      "sign": "Capricorn",
      "sign_longitude": 10.62,
      "house": 11,
      "retrograde": false
    }
  ],
  "houses": [
    {
      "number": 1,
      "sign": "Pisces",
      "degree": 14.5
    }
  ],
  "aspects": [
    {
      "planet_1": "Sun",
      "planet_2": "Moon",
      "aspect": "sextile",
      "orb": 2.3
    }
  ],
  "ascendant": { "sign": "Pisces", "degree": 14.5 },
  "midheaven": { "sign": "Sagittarius", "degree": 22.1 }
}
```

The exact structure should follow what Kerykeion outputs natively — adapt field names as needed but store the full output, not a subset. Future features may need data that seems unnecessary now.

## Cache and Regeneration Logic

Charts are cached on first generation and served from cache on subsequent views. Regeneration occurs automatically when:

- **Profile:** birth_date, birth_time, birth_place_lat, or birth_place_lon is changed
- **Entry:** reading_datetime, location_lat, or location_lon is changed
- **Global:** house system setting is changed (this invalidates ALL cached charts)

### How regeneration is detected

An `input_hash` is stored with each cached chart. The hash is computed from all input parameters (date, time, lat, lon, house system). When a chart is requested, the current input hash is compared to the stored hash. If they differ, the chart is regenerated and the cache is updated.

### When house system changes globally

All existing cached charts become stale. Two approaches:
1. **Lazy regeneration** — charts are regenerated one at a time when next viewed. Simpler to implement.
2. **Bulk regeneration** — all charts are regenerated immediately on settings change. Better UX but potentially slow with many profiles/entries.

**Recommendation:** Lazy regeneration for initial implementation. The input_hash comparison handles this automatically since the house system is part of the hash.

## Settings

### House System (global)
A new setting in Settings (under a dedicated Astrology section) allowing the user to select the house system used for all chart calculations.

Supported systems (Kerykeion supports all of these):
- Placidus (default)
- Whole Sign
- Equal
- Koch
- Regiomontanus
- Campanus
- Porphyry
- Morinus
- Alcabitius
- Topocentric

The setting is stored in `app_settings` using the existing key-value mechanism.

Changing this setting invalidates all cached charts (via input_hash mismatch on next view).

## UI

### Profiles — Natal Chart
A "View Chart" button in the profile view. Opens an expandable panel or modal displaying:
- The rendered SVG natal chart
- Summary data: Ascendant sign, Midheaven sign, Sun/Moon/Rising at a glance
- If required birth fields are missing, the button is replaced with a message indicating which fields are needed

The chart is generated on first click if not already cached. A loading indicator is shown during generation.

### Journal Entries — Event Chart
A "View Chart" button in the entry viewer. Opens an expandable panel or modal displaying:
- The rendered SVG event chart
- Summary data: Ascendant, planetary positions at a glance
- If required fields (reading_datetime, location) are missing, the button is replaced with a message indicating which fields are needed

Same caching and loading behavior as profiles.

### Chart Modal/Panel Contents
Both chart types use the same display component:
- SVG chart rendered at a comfortable viewing size with zoom/pan if feasible
- Below the chart, a summary table of planetary positions (planet, sign, degree, house, retrograde status)
- Aspect table (optional — could be a toggle to avoid overwhelming the view)

## Backend API Endpoints

### GET `/api/profiles/<id>/chart`
Returns the cached chart for a profile, or generates and caches it if not present or stale.

**Response:**
```json
{
  "chart_svg": "<svg>...</svg>",
  "chart_data": { ... },
  "house_system": "Placidus",
  "generated_at": "2026-03-15T10:30:00"
}
```

**Error responses:**
- 400 if required birth fields are missing (with message indicating which)
- 404 if profile not found

### GET `/api/entries/<id>/chart`
Same pattern as profiles, using entry's reading_datetime and location.

### DELETE `/api/profiles/<id>/chart`
Force-clear a profile's cached chart (useful if something goes wrong).

### DELETE `/api/entries/<id>/chart`
Same for entries.

## Kerykeion Integration Notes

### Generating a chart
```python
from kerykeion import AstrologicalSubject

subject = AstrologicalSubject(
    name="Querent Name",
    year=1990, month=6, day=15,
    hour=14, minute=30,
    city="Portland",  # or use lat/lon directly
    nation="US",
    lat=45.5152, lng=-122.6784,
    timezone_str="America/Los_Angeles"
)
```

### Key implementation details
- **Timezone handling:** The app stores lat/lon but not timezone. Kerykeion needs a timezone string. Use a library like `timezonefinder` to derive the timezone from lat/lon coordinates at chart generation time.
- **House system:** Kerykeion accepts house system as a parameter — pass the global setting value.
- **SVG generation:** Kerykeion has built-in SVG chart rendering via its chart factories. Use the natal chart factory for profiles and adapt for event charts.
- **Planet list:** Kerykeion supports 63+ celestial points. For initial implementation, use the standard set (Sun through Pluto, lunar nodes, Chiron, Lilith). The extended asteroid list can be enabled later if desired.

### Timezone resolution
Install `timezonefinder` alongside Kerykeion:
```
pip install timezonefinder
```
```python
from timezonefinder import TimezoneFinder
tf = TimezoneFinder()
timezone_str = tf.timezone_at(lat=45.5152, lng=-122.6784)
# Returns "America/Los_Angeles"
```

This must be done at generation time, not stored, since the same coordinates always map to the same timezone.

## Notes for Implementation

- **Kerykeion must be installed in the app's Python environment.** Add it to requirements.txt or equivalent.
- **timezonefinder must also be installed** for automatic timezone resolution from coordinates.
- Charts are a standalone feature — they do not feed into the Correspondences or Insights systems in this implementation. That connection can be added later.
- The chart_data JSON should store the full Kerykeion output, not a curated subset. Future features (transit comparisons, aspect pattern detection) will need data that may seem unnecessary now.
- SVG theming: Kerykeion generates SVGs with its own color scheme. These may need CSS overrides or post-processing to match the app's dark theme. Investigate Kerykeion's theming options before building custom SVG manipulation.
- The chart display component should be shared between profiles and entries — same modal/panel, same layout, same data presentation. Only the data source differs.
- **Error handling:** Kerykeion can fail on edge cases (extreme latitudes, very old dates, invalid coordinates). Wrap generation in try/catch and present a clear error message rather than a crash.
- This feature warrants its own git branch.
